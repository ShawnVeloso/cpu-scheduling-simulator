2. Preemptive Algorithms

Two preemptive algorithms are complete. Both algorithms share the one-time-unit loop that Progress Report No. 2 describes. The loop runs the CPU for one time unit, then it decides again.

A. Priority Scheduling (Preemptive). This algorithm and the non-preemptive version are one function. A flag selects the behaviour. The non-preemptive version decides only when the CPU becomes free. The preemptive version decides at every time unit. The decision has three steps:

  1. The scheduler examines all the processes and selects the best ready candidate. A process is ready when it arrived and still has burst time left. The comparison uses the priority, then the arrival time, then the PID.
  2. A process holds the CPU unless the candidate has a strictly higher priority. An equal priority does not cause a preemption. This rule stops an unnecessary context switch between two equal processes.
  3. If the candidate wins, the scheduler records a preemption event with the time, the two process IDs, and the burst time that is left. The timeline marks the block as cut.

The code does not copy a register set or a stack, because this is a simulator. A context switch is one assignment that changes which object the variable running points to. The preempted process keeps its remaining field, so it continues at the correct point later. It keeps its original arrival time, so the tie-breaking stays correct. Our context-switch time is 0.

How a new arrival interrupts the running process. The scheduler does not use an interrupt or a timer. The loop advances the clock by one time unit. At each new time unit it reads the arrival time of every process again. A process that arrives at the current time unit becomes part of the ready set immediately. The selection in step 1 then compares it with the running process. Therefore the preemption occurs at the exact arrival time unit.

B. Multilevel Queue (Q1 = Round Robin, Q2 = FCFS). This algorithm has two preemption types:

  • Preemption between the queues. Queue 2 runs only while queue 1 is empty. At each time unit the scheduler tests queue 1 before it dispatches. If a queue 1 process waits and a queue 2 process holds the CPU, the queue 2 process loses the CPU immediately. It returns to the front of queue 2, because queue 2 is FCFS. It keeps its remaining burst time.
  • Preemption by the time quantum. A queue 1 process has a counter that starts at the time quantum. The counter decreases by 1 at each time unit. At 0 the process returns to the back of queue 1 with its remaining burst time.

The order at one time unit is fixed, because it changes the result. First the new arrivals enter the back of their queue. Second the quantum-expired process enters the back of queue 1. A new arrival therefore runs before a process that lost the CPU at the same time unit.

Tests. The command node tests/run-tests.js runs 49 tests. All 49 tests pass. The preemptive tests cover these cases:

  • A higher-priority arrival takes the CPU, and the process continues later with the correct burst time.
  • An equal-priority arrival does not take the CPU.
  • Three processes arrive at the same time unit.
  • A queue 1 arrival takes the CPU from a queue 2 process, and the queue 2 process resumes at the front of its queue.
  • A new arrival enters queue 1 before a quantum-expired process.
  • The Gantt blocks cover every time unit one time, with no gap and no overlap.

3. GUI Integration

The backend and the frontend are connected. The simulator runs in a browser. The page uses HTML, CSS, and JavaScript with no framework.

The connection. The interface file src/ui/app.js imports one function, runSimulation(rows, options). This is the only link between the two parts. The interface holds no scheduling logic, and the core has no access to the page.

StepAction
1The user edits the input table, or uploads a CSV or TXT file.
2The user selects the algorithm and the time quantum.
3The interface reads the table into plain rows and calls runSimulation().
4The core checks the input, runs the algorithm, and returns the blocks, the results, the averages, and the events.
5The interface draws the Gantt chart and the metrics table from that answer.

The input passes correctly. A browser gives each table cell as text. The core converts the text to whole numbers and rejects any value that is not a whole number. We confirmed the connection in two ways. First, the browser shows the same numbers as the console test for the same process set. Second, the automatic tests use the same function and the same data sets.

What the interface does now:

  • The user adds or removes a process row, and edits each cell.
  • The user uploads process data as a CSV or TXT file.
  • The algorithm list offers the three algorithms. The page greys out the columns that the selected algorithm does not use.
  • The Gantt chart shows one colour for each process. It shows the IDLE time with a hatched block. It shows a red marker and a red edge at each preemption point.
  • The time axis shows a number at every block boundary.
  • The metrics panel shows the completion time, the turnaround time, and the waiting time of each process. It also shows the average turnaround time, the average waiting time, and the CPU utilization.
  • An invalid entry produces a message in a red panel. The page does not stop with an error.
