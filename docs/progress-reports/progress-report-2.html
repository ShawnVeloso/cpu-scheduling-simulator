2. Data Structures & Setup

The Process. We use JavaScript. A process is a plain object. The scheduler makes a copy of each input object before it starts. The copy holds five input fields and two work fields:

FieldTypePurpose
pidtextThe process identifier, for example P1.
arrivalwhole numberThe time unit when the process enters the system.
burstwhole numberThe total CPU time that the process needs.
prioritywhole numberA lower number is a higher priority.
queue1 or 2The queue level. The Multilevel Queue uses this field only.
remainingwhole numberThe CPU time that is still not done. It starts equal to burst.
completionwhole numberThe time unit when the process ends. The metrics use this value.

The scheduler changes the copies only. The input list of the caller stays the same. A test checks this rule.

The Ready Queue. The two algorithms use two different structures. Each structure matches the way that its algorithm selects a process.

  • Priority Scheduling: one array holds all the processes. At each time unit the scheduler examines the array and selects the ready process with the best key. A process is ready when arrival is not more than the current time, and remaining is more than 0. The selection function compares three keys in order: the priority, then the arrival time, then the PID. We selected a linear scan instead of a heap. The scan is short, and each member can explain every line of it.
  • Multilevel Queue: two arrays operate as FIFO queues. The code adds a process to the back with push() and removes a process from the front with shift(). Queue 1 is the foreground queue and uses Round Robin. Queue 2 is the background queue and uses FCFS.

The Timeline. The algorithms run the CPU one time unit at a time. A TimelineBuilder object records the owner of each time unit. It joins equal neighbours into one Gantt block. Every time unit from 0 to the last completion belongs to exactly one block. The block holds a process ID or the text IDLE. A test checks that the blocks have no gap and no overlap.

Structure of the code. The scheduling core has no access to the page and reads no file. The browser interface and the console test call the same function, runSimulation().

3. Backend Algorithms Completed

Priority Scheduling (Non-preemptive) is complete. This is our non-preemptive algorithm. The logic has three steps:

  1. When the CPU is free, the scheduler selects the ready process with the best key.
  2. The selected process keeps the CPU until remaining becomes 0. A new arrival with a higher priority does not interrupt it.
  3. When no process is ready, the CPU idles for one time unit. The timeline shows an IDLE block for this gap.

The FCFS logic of queue 2 is also complete. Queue 2 of the Multilevel Queue is non-preemptive inside the queue. It takes the process at the front and runs it.

The tie-breaking rules. We agreed on these rules before we wrote the code. All the algorithms apply them in the same way:

  1. A lower priority number is a higher priority. The number 1 is better than the number 5.
  2. If two processes have an equal priority, the earlier arrival runs first.
  3. If the arrival times are also equal, the lower PID runs first.
  4. The context-switch time is 0.

Work in progress. The preemptive version shares one function with the non-preemptive version. A flag selects the behaviour. The preemptive version makes a new dispatch decision at every time unit. We report this part in Progress Report No. 3.

4. Proof of Progress

Console/Backend Output. The command node tools/demo.js runs the backend with a hard-coded set of five processes. The set holds three edge cases:

  • A non-zero arrival time: P2 to P5 arrive after time 0.
  • An equal priority: P3 and P4 both have the priority 3. P3 arrived first, so P3 runs first.
  • An idle CPU: no process is ready between time 14 and time 16.

The output shows the input table, the Gantt timeline, the completion time of each process, the turnaround time, the waiting time, and the averages. The formulas are TAT = Completion − Arrival and WT = TAT − Burst.

We calculated the same set by hand before the run. The script prints both results beside each other. All seven values match. The last part of the output shows that the core rejects invalid input with a clear message and does not stop with an error.
